# 低周波フォレスト（lowfreq_forest_v1）

**2026-11-23（ファームウェア 0.17.0）から、観察のきっかけに使っています。** 250 ms ごとに「このフォレストの確率 ≥ しきい値」または「CH2 の 1–40 Hz の比 ≥ 3」の窓が現れたら、MCU に観察のきっかけを送ります（`host/ad3_bridge/activity_trigger.py`、検出器名 `LOWFREQ_FOREST_RATIO`）。2026-11-24 からは、300–1500 Hz の B2 の候補もきっかけに加えています（OR。B2 が始めたきっかけは `B2_guarded_mad` として送る。根拠は `docs/analysis/trigger_b2_union_20261124.md`）。同じモデルは MCU（Arduino Nano ESP32 / XIAO ESP32S3）の中でも動き、PC の判定と照合しています。これは観察のきっかけで、幼虫の検出ではありません。

以下は 11/20〜11/21 の作成時の記録です（「XIAO には送っておらず」などは当時の状態）。

- **入力**：250 ms ごとの CH1/CH2 1–40 Hz RMS（`host/ad3_bridge/lowfreq_activity.py` の LowTracker）から作る 6 特徴。すべて因果的（過去の値だけを使う）です。
  - `x` は ln(rms ÷ 直近 30 秒の 20 パーセンタイル)。
  - 特徴：`ch2_x`、`ch1_x`、`ln(ch2/ch1)`、`ch2_x` の直近 1 秒の最大、直近 3 秒の最大、直近 3 秒の平均。
- **モデル**：20 本・深さ 5 以下・820 ノード。C の配列にすると約 11 KB です（`firmware/xiao_esp32s3/include/lowfreq_forest_model.h`、`lff_predict()`）。
- **学習**：`analysis/ad3_label_review/train_forest.py` で作り、JSON と C ヘッダーの両方を出力します。
  - データ：2026-11-18 と 11-19 のラベル付き 24 記録。LARVA/DIG を 1 とし、NOISE の重みは 3 倍、2 日は同じ重みにしています。
  - しきい値：学習データで、ratio≥3.0 と「ラベルのない時間を検出する割合」が同じになるように決めています（in-sample）。
- **検証**（train_forest.py の出力。誤報率は閾値 3.0 とそろえています）
  - 記録ごとの leave-one-run-out（24 記録）：LARVA/DIG 範囲は 98/120（閾値 3.0 は 92/120）。
  - 11/19 を除いて学習し 11/19 で評価：51/57（同 46/57）。
  - 11/18 を除いて学習し 11/18 で評価：28/63（同 46/63）。**日をまたぐと閾値より悪い**ため、暫定扱いです。
- **学習に使った記録**では、紫の帯は答えを見た結果になります（画面に注記を出します）。
- **検出ではありません**。物音でも出ます。XIAO には送っておらず、B2・候補・判断は変わりません。
- **テスト**：`host/ad3_bridge/test_lowfreq_forest.py`
  - C ヘッダーを zig cc でビルドし、Python の推論と一致することを確かめます。
  - 特徴が因果的であることも確かめます。

## MCU コア（スライス①、2026-11-21）

- **前提**：MCU は自分で 1–40 Hz を取りません。PC ブリッジが AD3 から計算した 250 ms ごとの CH1/CH2 1–40 Hz RMS（判断ではなく測定値）を受け取り、MCU の中でフォレストを適用します。
- **コア**：`firmware/xiao_esp32s3/include/lowfreq_forest_core.h`（`bll::lff::Tracker`）。
  - Arduino・I/O・ヒープを使いません。状態は 1,056 バイトです。
  - 処理：`push(t_ms, ch1, ch2, arm)` を 1 窓ずつ呼ぶと、30 秒の 20 パーセンタイルの床 → 6 特徴 → `lff_predict()`（`lowfreq_forest_model.h`、train_forest.py が生成）→ 区間化（1 秒以内の隙間はつなぐ）の順に計算します。
  - `arm`：XIAO 自身がアームを動かしていた窓（前後 0.3 s を含む）を true にします。その窓は床にも帯にも使いません。
- **一致の確認**
  - `scripts/run_core_tests.ps1`：C++ の自己チェック。
  - `host/ad3_bridge/test_lowfreq_forest.py`：合成データで、PC の `judge()` と区間が完全に一致すること。
  - `analysis/ad3_label_review/check_forest_core.py`：記録した 28 記録・14,214 窓を、PC 上でビルドしたコアに流して比べます（デバイスには送りません）。
    - 結果：active が食い違ったのは 3 窓（0.02%、float32 の値が分岐点のすぐ近くにあったため）、区間は 323/323 で一致、p の差は最大 0.038。
    - 値を 0.01 µV に丸めた場合（シリアルで送る想定）：区間 322/323 で一致。
- **未実施（スライス②以降）**
  - ブリッジから XIAO へ送るコマンド（例 `lowfreq-rms <run> <t_ms> <ch1_uV> <ch2_uV>`、値は 0.01 µV 以上の精度）。
  - ファームウェアへの組み込みと、結果を返す経路。
  - 振り返り画面での PC 版との比較。
  - Evidence への記録と、観察方策での利用は承認が必要です。

## ブリッジ → XIAO（スライス②、2026-11-21、ファームウェア 0.15.0）

```
AD3 ─(100 kHz)→ PC ブリッジ：LowTracker で 250 ms ごとの CH1/CH2 1–40 Hz RMS を計算（測定値）
      └─ lowfreq-rms <t_ms> <ch1_nV> <ch2_nV> ──→ XIAO：lowfreq_forest_core.h（自分のアーム動作で除外）
      ←── LFF t=.. p=.. a=.. arm=..[ span=t0,t1,peak,n] ──┘
      → 記録フォルダの xiao_lowfreq.jsonl → 振り返り画面の紺の帯
```

- **ファームウェア 0.15.0-observation-lowfreq**（`src/lowfreq_runtime.cpp`）
  - コマンド：`lowfreq-begin <run8> <ad3_ms>`、`lowfreq-anchor <ad3_ms>`、`lowfreq-rms`、`lowfreq-end`。
  - **Evidence ログには書きません。** 観察方策も変えていません。新しいイベント型もないので、古いファームウェアとの互換は一方向に切れません。
  - **アームの除外**：XIAO が自分のサーボの動作区間を `millis()` で記録し、前後 0.3 s を除外します。
    - AD3 の時刻と XIAO の時刻の対応は、ブリッジが送るアンカー（begin と 30 秒ごとの anchor）で取ります。
    - 移動後の静定時間は含めません。PC 版（MOVE_BEGIN→CAPTURE_BEGIN、静定を含む）とはこの点が違います。
  - **リソース**：RAM 14.8%、Flash 13.9%（xiao_evidence ビルド）。
- **ブリッジ**（`lowfreq_link.py`、`protocol.XiaoLink.lowfreq()`、`manager.py`）
  - XIAO へ転送している LIVE 取得のときだけ動きます。
  - 窓を送るのは、送信スレッドが空いているときだけです。候補の送信と観察エピソードの間は、窓を貯めておき、終わってから追いつきます（1 回に 40 窓まで）。
  - 古いファームウェアはコマンドをそのまま ECHO で返すので、UNSUPPORTED と記録して送るのをやめます。
  - エラーや時間切れがあれば、その記録の間は止めて ERROR を記録します。どちらの場合も、取得・候補・観察は止めません。
  - manifest に `xiao_lowfreq`（窓の数、区間の数、たまった窓の最大数、エラー）を記録します。
- **振り返り画面**：紫の帯（PC で計算したフォレスト）の下に、紺の帯（XIAO が取得中に計算したもの）を表示します。見出しに XIAO の窓数・区間数・アームで除外した窓数を出します。
- **テスト**
  - `test_lowfreq_link.py`：偽のポートで、送信と応答、溜まった窓の追いつき、古いファームウェア、エラー時の停止を確かめます。
  - `test_review.py`：紺の帯のデータが正しく出ることを確かめます。
- **実機での確認（未実施）**
  1. 0.15.0 を書き込む前に、LittleFS の領域をバックアップする（`read_flash 0x670000 0x180000`）。
  2. 書き込み後、`info` が `fw=0.15.0-observation-lowfreq` になっていること。
  3. 転送ありの LIVE 取得（150 秒）をする。
     - `xiao_lowfreq.jsonl` が BEGIN → WINDOW（約 600）→ END になっていること。
     - manifest の `xiao_lowfreq.status` が `ENDED` で、`errors` が空であること。
  4. 振幅を上げたエピソードを含める。
     - 候補の ACK と観察が今までどおり動くこと（`delivery.jsonl`）。
     - エピソードの間に溜まった窓（`max_backlog`）が、後から追いつくこと。
  5. 振り返り画面で、紫と紺の帯がほぼ一致し、アームの動作中に紺の帯が出ていないこと。
  6. Evidence の件数が、候補・判断・結果の分しか増えていないこと（lowfreq では増えないこと）。

### 0.15.1（2026-11-21）：観察中のアーム移動を除外できていなかった問題の修正

- **見つかったこと**：0.15.0 の LIVE 11 記録（11/21 1:17〜）を確認した。
  - XIAO の arm マスクは PARK（基本位置に戻る動き）しか捉えていなかった。
  - 観察ステップ内の MOVE（TOP/BACK への移動）は捉えていなかった。
- **原因**：`runMove()` は移動が終わるまで loop() を止めるため、loop() で `servoMoving()` を見ていた `lowfreqPoll()` が移動中に一度も呼ばれなかった。
- **影響**：XIAO が active にした窓のうち、PC のアーム区間に入っていたもの。
  - 77 窓（MOVE の動作中 51、静定の 0.8 s 18、区間の後 8）。
  - 例：1:17:58 の記録は、PC のアーム区間が 10 個のうち XIAO が除外できたのは PARK の 3 つだけだった。アーム区間内の窓のうち 37 窓を active にしていた。
- **修正**
  - サーボドライバが、動作の開始時刻（`servoMotionStartMs()`）と最後のステップの時刻を自分で持つようにした。
  - `lowfreqPoll()` はその 2 つの時刻から区間を作る。loop が止まっていた動作も、後から記録できる。
  - 各窓を判定する前にも `lowfreqPoll()` を呼ぶ。
  - 除外する範囲は「動作＋静定 0.8 s（スケジューラの settleMs）、その前後 0.3 s」。
- **実機確認（2026-11-21、0.15.1 書き込み後の LIVE 3 記録：11:28:33 90 s、11:30:16、11:32:03）**
  - PC のアーム区間に入る窓で、XIAO が active にしたものは 0（3 記録とも）。
  - 窓ごとの active の一致率は 96.7% / 99.3% / 99.8%。
  - 差はすべて arm マスクの違いから来ている。PC の計算を XIAO の arm マスクでやり直すと、3 記録とも 100% 一致する（p の差は最大 0.0001）。
    - XIAO は静定 0.8 s も除外するので、除外する窓が PC より多い（+20 / +3 / +8 窓）。
    - 床（直前の非アーム窓の 20 パーセンタイル）も除外した窓を抜いて計算するので、その後の窓の p が少しずれる（最大 0.07）。しきい値 0.578 付近の窓では active が入れ替わる。
  - 11:28:33 の 79–83 s では、XIAO だけが最後のパークを除外していた。PC 側は 10 窓を active にしていた。
    - PC のアーム区間が抜けていたのが原因（下記のブリッジ修正）。XIAO の判定は正しかった。
- **ブリッジ修正（同日）**：アームの行が `actuation.jsonl` に書かれるのは、次の候補が受理されたときだけだった。
  - 最後の候補のあとに読んだパーク終了（PARK_DONE）は、ファイルに残らなかった。lowfreq の空き時間のやり取りで読まれていた。
  - 空き時間とブリッジ停止時にも書き出すようにした（`manager.py` の `write_arm`、テスト `test_lowfreq_link`）。
  - 既存の記録は直していない。11:28:33 の PC 側の帯は、最後のパークの間も active のまま表示される。
- 区間の後（撮影中）の窓は、PC 版も除外していない。
